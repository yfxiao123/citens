# LitSearch 评测复盘：我们踩过的所有坑

## 先交代背景

LitSearch 是 Princeton 发的一个文献检索评测集，597 道真实的研究者提问。我们让系统走真实 API（Semantic Scholar、OpenAlex、Crossref）去检索，然后看金标论文有没有被找回来（对得上 DOI 就算 DOI 匹配，对不上就退到 arXiv id，再退到标题匹配）。每次跑批抽 15 题，四个难度档分层抽样。

有一条纪律必须写在最前面：**15 题里错 1 题就是 6.7 个百分点**。API 会抖、LLM 每次生成的查询词都不一样，所以任何一次跑批里小于 13 个点的差距都不能当真。这一页里所有结论，最终都靠"命中的是哪几道题"和机制层的证据钉死，而不是靠某一次的百分比。

## A. 召回：问题出在"说的不是一种语言"

### A1. planned 腿一度 0/15，原因特别好笑

**现象**：把 planner 生成的关键词拿去检索，15 题全部落空。但同样这批题，agent 循环反而能找到。一开始我们以为是关键词这条路本身不行。

**排查**：把 planner 每次实际生成的查询词和金标论文的标题摆在一起看，马上看出问题了——代码里取的是查询列表的前三条，而排在前面的都是"单概念"查询，比如就一个 "prompt tuning"。可这类问题的金标标题长什么样？"The Power of Scale for Parameter-Efficient Prompt Tuning"——它是好几个概念的组合。你用一个词去搜一篇标题是四个词的论文，当然搜不到。

**影响**：一条本该有效的腿被自己的取词顺序废掉了，还差点让我们误判整个方向。

**解决与收益**：改成组合优先（同长度排序取最长）。0% 变成 20%（seed 13）。后来换 seed 42 复测是 13.3%，也就是说这个改法的真实水平在 6.7%–20% 之间浮动——改善了，但远谈不上解决。

### A2. 真正的大 boss：词汇墙

**现象**：15 题里 12 题，所有静态检索腿全军覆没。S2 的相关度搜索 15 题零命中。我们把每个查询格的取数深度从 20 加到 40，结果一个字都没变——金标论文压根不在任何格子的前 40 名里。

**排查**：做了一次彻底的解剖。第一层看词面：问题里的词和金标标题里的词，交集几乎是空的。第二层试"行话"：手动构造子领域的标准短语去搜，照样进不了前 40。第三层试"跳"：从检索到的近邻论文出发，走引文（往前、往后）、走 S2 的学习型推荐、再让 LLM 重排——四条路全部零命中（15 题里 7 题四个指标全零）。唯一稳定有效的检索形态，是拿一篇和金标几乎一样的标题去做精确匹配（Crossref 第一名命中）。

**结论**：问题的措辞和金标论文所在子领域的措辞是两套语言，而我们四个检索源全是词法匹配。金标根本没进过候选池——排序再好也无米下锅。这不是我们的独有问题：LitSearch 原论文里，词法方法和商用引擎的 recall@5 顶到 43%，稠密语义检索能到 75%，中间这 30 个点就是我们撞的墙。

**影响**：单查询形态的召回天花板就在 13% 附近。之前"这只是个排序问题"的判断被推翻了一半——一半题确实是排序问题，另一半是根本够不着。

**解决与收益**：从两个方向翻墙。一是 HyDE 假想标题（从问题侧）：让 LLM 直接写"能回答这个问题的论文标题"——既然精确标题是唯一可靠形态，那就系统化地生成它。二是 PRF pivot（从语料侧）：读已检索到的邻居论文的摘要，把里面的任务名、基准名、方法名**原样**抄下来当查询词。两条路各自抓到过所有旧腿全零的题。所有形态的命中并集是 33.3%，比任何单一形态的 13.3% 高一倍多。没翻过去的部分见文末清单。

### A3. 挖词必须逐字抄，不能让 LLM"润色"

**现象**：pivot 早期版本挖出的实体名，会被 LLM 顺手意译改写，然后检索就失败。

**排查**：做对照实验："emotional support conversation"（摘要里的原话）能搜到，"emotional support dialogue systems"（LLM 觉得更通顺的说法）搜不到。

**解决与收益**：在提示词里立死规矩——任务名、基准名、方法名必须逐字复制，"SemEval-2022 Task 4"不许写成"shared task 4"。改完之后机制当场验证：挖出的逐字短语命中了它的金标，pivot 单腿 13.3% 对 planned 的 6.7%，而且命中是超集。

## B. 融合与排序：捞回来了别又弄丢

### B1. 轮流交错的融合方式会埋掉好结果

**现象**：一篇金标在某个查询格里排第 5，用"各格轮流取一名"的方式融合后，掉到了第 29。

**原因**：轮转只看位次不讲证据强度，一格之内的第 5 名和第 40 名被同等对待。

**解决与收益**：换成 RRF（倒数排名融合，各格 1/(60+名次) 求和），单格第 5 名的金标回到融合前列。零额外成本。

### B2. 融合会稀释孤证——这是最阴的一课

**现象**：pivot 单独跑 13.3%，和 planned 的格子合到一起融合，反而掉到 6.7%。最尖锐的一个案例：某题的金标在"原始问题"这一格里是 Crossref 第 0 名，融进 12 个格子之后，它**掉出了前 100 名**——也就是说后面的 LLM 排序器根本没机会看到它。

**排查**：把单腿和融合的命中集合做对比，再离线重放融合过程，定位金标的准确名次，确认稀释发生在两个层面：top-20 的呈现层，和 top-100 的"进 LLM 视野"层。

**原因**：RRF 奖励的是"多个格子都提到我"的共识，而翻过词汇墙的金标恰恰只出现在**少数格子里**——它是孤证，共识机制天然打压它。

**解决与收益**：族配额——planned、原始问题、假想标题、挖词四个家族各自融合、各留 30 个席位，合并去重后送给 LLM 排序。这样每个查询形态的头部必然到达语义排序面前。效果实测：有一题的金标以池内第 52 位进入，被 LLM 直接排到第 1——在旧的全局 RRF 里它连池子都进不了。

### B3. LLM 排序：能用，但看条件

**现象**：三副面孔。金标不在候选里时，重排零效果（废话，但当时需要验证）；金标在 union 前 30 里时，r@5 从 6.7% 翻倍到 13.3%；候选集膨胀到 100+ 时，会把融合排名已经在前 20 的金标又挤出去——同一道题两次跑结果还不一样。

**排查**：离线诊断给了很干净的对照——同一道题，金标在池内第 52 位时 LLM 把它排到第 1；另一道题融合排名前 20，LLM 反而排没了。

**结论**：LLM"看到了大多能认出来"，但让它对 100 多个候选做完整排序，cheap 模型的方差大到不可用。对照组：LitSearch 论文的重排增益（+4.4 个点）用的是他们最强的 GPT-4o，而且池子来自 recall 74.8% 的检索器——人家是锦上添花，我们是在烂池子里捞针。

**解决与收益**：改成两阶段级联——cheap 模型先做点式打分（每个候选独立打 0–10 分，分批但看**全池**，没有截断损失），取前 50 交给 listwise 做精排；给 agent 交付用的那次排序换 strong 档。实测（生成冻结后的验证轮）：adaptive 级联 13.3%@20 / 6.7%@5，**超过了它自己的输入序**（族配额融合序只有 6.7%@20）；最有说服力的是 index-6 这道题——历史所有腿、包括本轮全局 RRF 都没进前 20，级联直接排到**前 5**。agent 侧 Q3 的 top-5 命中连续两轮复现。残留：精排层偶发降权（Q14 一轮前 5、一轮 6–20），Crossref 抽风仍未消（Q9 连续两轮返回 0 条）。

### B4. 重排的作用窗口太浅

**现象**：早期重排只吃融合前 30 名，金标排在 31–100 名时永远轮不到它。

**解决**：这个问题最后被 B2 的族配额和 B3 的级联从结构上解决了——点式粗排看的是全池，不再有固定窗口。

## C. Agent 循环：捞到了，交出去又浪费

### C1. 金标进了池子，却被输出顺序埋了

**现象**：agent 模式 5 题里 3 题金标进了池子（池子 89–169 篇），但看前 5 名，5 题全零。翻记录才发现：池子的顺序就是插入顺序，谁先被搜到谁在前。

**影响**：这是最典型的"召回做对了、交付搞砸了"——agent 费力翻墙捞回来的东西，用户在列表前几名根本看不到。

**解决与收益**：find 模式结束时，先按（命中过几个查询、引用数）排一个初步序，再让 strong 档 LLM 按问题相关性排一次（原始顺序留在 `papers_unranked` 里可审计）。修复后的满血复测里，第一次出现金标进交付列表前 5（此前该指标历史恒为零）。

### C2. 搜索预算是按 survey 的经济学设的，find 用不起

**现象**：agent 的失败案例清一色死于 budget:steps——被掐断时才用了八九次 LLM 调用，还在改写查询词的路上，并不是在原地打转。

**结论**：找特定论文需要轮次去读候选、确认标题；按"池子够大就该停"设定的预算对 find 是错配。

**解决与收益**：两次放宽（12/14/5 → 16/18/6 → 20/22/6）。有效但边际递减——有一题 20 步还是会撞墙。预算不是根本解，查询形态才是（那是 A2 的事）。

### C3. find 模式被池子上限误杀（低级但真实的矛盾）

**现象**：一个 find 失败案例以 budget:pool 结束——池子 169 篇时被硬停，当时还在改词。而 find 模式的提示词明明白白写着"池子大小不是成功"。

**解决**：池子上限只对 survey 生效。一行改动，find 不再被自己不承认的指标掐死。

### C4. "假完成"——唯一确认了还没修的问题

**现象**：有两题 agent 以 done 收尾，说得头头是道，但金标根本不在池子里。

**结论**：done 这个动作没有校验"你说的那些论文真的在池子里吗"。

**影响**：find 模式的可信度——用户拿到一份自信但漏了答案的清单。

**状态**：待办。方向是 done 门槛加核验：命名的标题必须能在池中匹配到，否则弹回继续。

## D. 提供方与基础设施：被天气背刺的几次

### D1. OpenAlex 额度耗尽 + 缓存投毒，连环坑

**现象**：snowball 突然一个候选都返回不了；重跑一次，瞬间完成，照样全零；个别题又能拿到 13 个候选，看起来像随机故障。

**排查**：直接调 API 才看到真身：429，"Insufficient budget，午夜 UTC 重置"。更糟的是追查缓存时发现——**空的失败结果被写进了磁盘缓存**，所以重试"瞬间完成"，因为它直接读了缓存的零。

**影响**：当天所有带 OpenAlex 的测量系统性偏低，诊断结论被污染过一轮。另外暴露了 snowball 是 OpenAlex 单提供方，OA 一死就整体瘫痪。

**解决与收益**：三个检索方向全部加了 S2 兜底；空结果永不缓存；手动清掉 41 个被污染的缓存文件。之后 OA 再死，snowball 照常工作。

### D2. S2 的两个脾气

**现象**：用 `DOI:10.48550/arxiv.*` 查 S2 图接口，404 说论文不存在；调试脚本频繁 429。

**排查**：换个前缀直接请求对照。结论：S2 只认 `ARXIV:` 前缀；而且我们进程里有个全局 1 QPS 的节流器，裸写 httpx 的调试脚本会跟主流程抢配额。

**解决**：加了 id 归一化函数（图接口和推荐接口统一走它）；调试脚本一律借用主流程的节流请求器。

### D3. arXiv 来源的论文天生"零引用"，会被池子裁掉

**现象**：一篇 1.7 万引用的经典论文（Lewis et al. 2020），只被 arXiv 腿捕获时带着 citation_count=0，在进池裁剪时被随意切掉，从没到过过滤阶段。

**排查**：单篇追踪命运。根因：arXiv API 不提供引用数；而裁剪逻辑在来源组内排序，零引用来源整个被饿死。

**解决与收益**：捕获时用 S2 批量接口做一次增强（arXiv id 换回真实引用数和 DOI，实测单篇恢复 17,476 次引用）；裁剪改为保留一半名额给全局引用最高的论文。顺带修了一个隐患：引用增强和评测的金标匹配必须用**同一个** arXiv id 提取函数，两处提法不一致时会静默漏配。

### D4. 长跑批死一次，数据全没

**现象**：50 题的跑批在第 26 题挂掉，内存里的明细全部丢失。

**解决**：改成每题落盘一行 JSONL，跑完即写。后来几次主动 kill 都靠这个保住了已完成的数据——这个坑只踩一次就够本了。

## E. 测量本身的可信度

### E1. 三个噪声源，差点骗过我们好几次

**现象**：同一条命令跑两次，planned 从 13.3% 掉到 6.7%；Crossref 对某题这次返回 20 条、下次直接 0 条；planner 每轮生成的查询词都不一样。最典型的是 Q3 这道题：满血复测第一轮假想标题命中（融合前 20），第二轮 planner 重新抽了一组词，融合配比一变，同一个命中就没了。

**排查**：跨轮对比"命中题目集合"而不是百分比，把每次翻转归因到具体噪声源。

**结论**：三个独立的噪声源——LLM 生成方差（planner、pivot 每轮重抽）、API 抖动（Crossref 偶发零返回）、LLM 排序方差（listwise 不稳定）。15 题的样本量下，这三样叠加能把任何 13 个点以内的差异变成随机数。

**影响**：有一度我们把 Q9 的丢失当成代码回归去查了半天，其实是 Crossref 那次抽风。

**解决与收益**：给 bench 加了生成缓存——planner/hyde/pivot 的生成结果按题冻结落盘（版本号控制重置；首轮已冻结 45 条），配合本来就有的搜索缓存，第二轮起对照就只测排序层了。判读纪律也改了：看命中集合、看机制证据，不看单次点值。Crossref 的偶发零返回是唯一没法在客户端侧消除的噪声源，只能靠重复跑数票。

### E2. 样本太小，seed 之间也别硬比

**现象**：seed 13 是 20%，seed 42 是 6.7%–13.3%，看起来像退步，其实两套题难度本来就不同。

**纪律**：代码 A/B 用同一个 seed；跨 seed 只看方向；重要结论必须有命中集合或机制层证据背书。
